Act II · The Mess

The architecture isn’t wrong. It’s premature.

The design is technically coherent. It just assumes a team, a customer base, and a maturity we don’t have yet.

What it gets right

  • Separate analytics from OLTP. Yes.
  • Open formats (Parquet) over proprietary. Yes.
  • Read replicas, batch ingestion, masking. Yes.
  • Quantum / Treasury Data Hub alignment as a north star. Yes.

What it skips

  • Named customers with named questions
  • A team that can operate it without the original prompter
  • The Logi deadline that pays the bills
  • The phrase “simplest viable alternative”
“Each phase is additive; nothing is rewritten.” — The architecture doc. This is almost never true in real systems.

Act II · The Mess

Five questions we forgot to ask.

Every major architectural choice from here on must answer these. If it can’t, it doesn’t ship.

  1. What real customer need does this solve? — Name the customer. Name the report.
  2. What is the simplest viable alternative? — And why isn’t that the plan?
  3. Who will maintain this in 2028? — Not the original author. Someone else.
  4. What is the cost of changing our mind? — If we’re wrong, how expensive is the U-turn?
  5. What evidence would make us stop? — Write the kill criteria before we start.

If a feature can’t survive these five questions, it’s not a feature. It’s future maintenance debt.

Act III · The Reset

Five rules we don’t bend.

RULE 01

Customer need before architecture

Every epic names the customer, the report, the owner, and what breaks if we don’t build it.

RULE 02

Tactical and strategic, never mixed

Short-term Logi replacement is not blocked by a future-state platform debate.

RULE 03

Batch first, unless real-time is proven

Daily batch is the default. Hourly is opt-in. Streaming needs a named use case that pays for itself.

RULE 04

No AI/ML without a feature dataset

Use case, labels, action loop, false-positive plan — or it stays a slide.

RULE 05 — THE ONE THAT KILLS PROJECTS

Maintainability is a release criterion

A second engineer must be able to explain it, operate it, and change it. If they can’t, it’s not an asset — it’s a liability with good intentions.

Epic 01 · Short Term

Read-only datamart access. The keystone.

Why first: clearest customer need, real legal/contractual continuity, and the team finally touches a real customer environment.

In scope

  • Read-only access to existing datamart tables
  • FIS-managed, customer-managed, private, on-prem
  • Read replica where required
  • Secure access: VPN, AWS Client VPN, PrivateLink
  • Schema docs + existing Logi query pack
  • Version compatibility matrix

Explicitly out

  • New analytical model
  • Data lake or Iceberg
  • Performance remediation
  • Bespoke dashboard rebuilds by core eng
  • Anything with the letters AI or ML

Done when at least one customer can query the datamart safely, with a runbook a non-dev team can execute.

Epic 02 · Short Term

Logi dashboard reproduction in BI tools.

Why: prove the tactical path works for real Logi dashboards before we tell PS to repeat it forty times.

The work

  • Stand up Apache Superset internally
  • Compare Power BI and QuickSight on representative dashboards
  • Parse .lgx files; extract queries
  • Rebuild representative dashboards: volumes, FX, rejections, statements

The output that matters

Every gap classified into one of:

  • Missing datamart data
  • BI visualization difference
  • Performance problem
  • Client customization
  • Genuinely unsupportable use case

Findings drive Epic 5 and Epic 8. No findings = no platform.

Epic 03 · Short Term

Datamart operationalization & runbook.

Why: a tactical path that PS, OPS, and CIO can’t execute is just a slide deck. This is the un-glamorous epic that decides whether we actually ship.

The work

  • Deploy Trax internally; load historical data
  • Run legacy ETL; validate datamart population
  • Confirm read-replica behavior under load
  • Build per-version schema compatibility matrix
  • Define issue triage taxonomy: access / schema / data / ETL / perf / BI

Acceptance bar

  • Health checks confirm datamart ETL ran successfully
  • PS-owned client readiness questionnaire exists
  • Support ownership model signed by OPS and PS/CX
  • Known gaps documented with escalation path

Test: can someone outside Eng run it end-to-end?

Epic 04 · Short Term

Pilot: Atlas Copco & UNICC.

Why: real customers find the gaps a hundred internal demos never will. The pilot is the truth serum.

What we measure

· Access usability

· Schema completeness

· Performance under real queries

· Dashboard reproducibility

· PS support burden per customer

· Defects vs enhancement requests

Owned by PS/CX, not core engineering. If engineering owns the pilot, we’re back where we started.

DECISION OUTPUT

Is the package scalable to the next customer batch?

If yes: roll out. If no: fix what’s broken before we scale the pain.

Epic 12 · Short Term

The secret weapon: a synthetic datamart.

A rich, realistic, fake Payment Hub dataset. Sounds boring. Changes everything.

What it contains

  • Payments, statements, statuses, approvals, signers
  • Counterparties, currencies, banks, charges, partials
  • Edge cases: missing accounts, multi-sig, non-BIC clearing
  • Intraday/EOD dupes, multi-charge entries, repaired payments
  • Client-specific extension fields
  • Enough history to test time-series dashboards

What it unlocks

  • Dashboard development without prod access
  • .lgx → BI transformations testable in CI
  • Demo data for customer conversations
  • Lake-experiment substrate without legal review
  • Onboarding fixture for every future engineer

One reusable asset that de-risks every other epic in this deck.

Epic 06 · Medium Term

The thin slice: datamart → Parquet.

Why: before we commit to a lakehouse, find out if a flat-file export is what customers actually wanted all along.

The thin slice

datamart → ETL → Parquet on S3
            (partitioned by date)
                  ↓
       SQL engine of customer’s choice

No Iceberg. No Bronze/Silver/Gold. No catalog ceremony. Validate with Quantum Data Hub, Athena, Power BI, QuickSight, Superset.

DECISION OUTPUT

After the thin slice, choose one:

  1. Simple export is enough — ship it
  2. Align with Quantum Data Hub
  3. Build dedicated PHUB lake (Epic 9)

Epic 07 · Medium Term

Quantum alignment spike. Build, reuse, or integrate?

Why: Quantum / Treasury Data Hub already has a POC running. Two parallel platforms is the worst outcome of all.

UNDERSTAND

  • Quantum’s workflow reports, metadata YAML, Parquet output
  • S3 notification → Iceberg ingestion model
  • DuckDB / Power BI / Snowflake access patterns
  • Time-series & time-travel capabilities

MAP THE FIT

  • Trax is message-centric; Quantum is workflow-centric
  • Static data ownership differs
  • Custom fields, lifecycle status, volume profile
  • Output: documented gap analysis

FORCED DECISION — ONE OF FOUR, IN WRITING

(1) Reuse Quantum Data Hub. (2) Integrate via Parquet handoff. (3) Build PHUB-specific lake, aligned on open formats. (4) Pause until requirements mature. Decision record. Signed. Dated.

Epic 08 · Medium Term

Analytical model evolution — only where evidence demands.

Why: the proposed fact/dimension model is interesting on paper. Validate it against real Logi reports and Lawrence’s open questions before we commit.

Open questions to resolve

  • Account dimension richness, party/bank/country data
  • Clearing code/system/BIC handling
  • Multiple approvals & signatures (cardinality)
  • Functional vs technical repository status
  • Statements: intraday, debit-credit, partials
  • Old datamart backward compatibility

Hard rule

Every new fact and dimension must cite:

  • A specific customer report it enables
  • A specific gap it closes vs the current datamart
  • An SME who signs off on the source-to-target map

Minimum viable model. Not exhaustive.

Epic 09 · Long Term

Data lake MVP — reduced and justified.

Why now (if at all): the thin slice proved insufficient, Quantum reuse was ruled out, and ranked use cases require curated tables.

What we build

  • Source read replica, batch ETL
  • Parquet or Iceberg — decided, not assumed
  • Bronze/Silver/Gold only if each layer earns its keep
  • Masking, RLS, customer partitioning, audit
  • One query engine, one cost model, one runbook

Acceptance bar

  • Top use cases answerable from Gold without consumer transformation
  • Security & PII review signed
  • Cost model measured (not modeled in a spreadsheet)
  • Two engineers can operate it without the original author.

This is what the original architecture wanted to be. Reached by the long way round — for very good reasons.

Epics 10 & 11 · Long Term

AI/ML & MCP. Discovery, not delivery.

EPIC 10 · ANOMALY DETECTION

Turn “AI” into one testable use case.

  • Pick one: unusual amount, beneficiary, country, or timing
  • Statistical baseline first — the product already has SQL fraud patterns
  • Only add ML if the baseline isn’t enough
  • Define: action, false-positive plan, explainability, audit

EPIC 11 · MCP / LLM ACCESS

Conversational analytics, governed.

  • Persona first: support, ops analyst, client reporting user
  • Semantic layer over raw SQL
  • Synthetic / masked data for the prototype
  • Risk classified, not assumed

Hard rule: nothing in this slide is on the critical path. Nothing in this slide blocks Logi replacement. Nothing in this slide leaves discovery without a named user, a named decision, and a named action.
